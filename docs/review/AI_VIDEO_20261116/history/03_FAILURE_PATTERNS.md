## F1｜用「语义错误的首帧」顶替已批准的高清关键帧（用户点名）

**现象**：要求「全程无人」的镜头，首帧却是一张有人的截图，而且是从别的成片里截的 1344×756。

**证据**（`session-213b3228…`，DeepSeek 段）：
- 2026-11-16 **10:46:02 / seq4591**，模型 `deepseek-official/deepseek-flash` 跑 bash：
  `ffmpeg -ss 10.9 -i 07_SHOT_GENERATION/REGEN_2K_V03_20261116/BATCH_C/C01_001_GROUND12/2026-11-16_00-54-11-regeneration.mp4 -frames:v 1 -vf scale=1344:756 … S01_001_no_person_first_1344x756.jpg`，
  脚本注释写 `# 无人帧：raw 约10.9s（车与井口、无人）`。
- 该文件实际内容（本审计用 `read_image` 核对，sha256 `a54b06b7…d28afa62`，1344×756，141,934 B）：**画面右侧有一名戴黄安全帽、正在下梯的工人**。
- **10:46:26 / seq4607** 用它作 `first_frame` 提交 768P，prompt 里写 `absolutely NO PEOPLE anywhere in the frame`。
- 工程里**本来就有**已批准的高清关键帧：`07_SHOT_GENERATION/USER_SELECTED_20261115_2203/S01_001/S01_001_f01_c7aebe8056.png`（2048×1152，3,539,177 B，sha256 `c7aebe80…4af02d57`，画面无人、卡车/井口/围挡齐全）——本审计同样 `read_image` 核对。
- 用户 **10:54 seq4726**「会不会是因为输入的图片不对」、**10:55 seq4763**「**为什么非要截取帧？我们的生成出来的高清关键帧中没有相关的？**」。
- 直到 **10:55:39 / seq4766** 才改用它，一次成功（`463851268137475`，768P 10s）。

**根因**：把「上一版生成片里没有人的那一段」当成「无人素材」，并用「缩小到 1344×756」去凑视频模型的首帧尺寸；同时**不知道/没查已批准关键帧索引**（`USER_SELECTED_…` 目录 + `ADOPTION_USER_v01.json`）。

**修正**：首帧只能来自「已批准关键帧 / 场景母版派生图」；若必须从成片截帧，先 `read_image` 自检语义（有没有人、朝向、道具），再提交；尺寸不是理由（工具会缩放，语义优先）。

## F2｜把「参考音频」当台词音频，且提示词不写台词（用户点名）

**现象**：prompt 只写 `speaking the line of <Audio 1>`，把声线样本当成台词内容；生成后还先判通过。

**证据**：
- `session-213b3228…` **10:46:27 / seq4609**（S01_004_LADDER）与 **seq4611**（S06_001-1_ZHOUYUAN）的 prompt 原文：`…speaking the line of <Audio 1> in his focused young voice with natural lip sync…`——**没有 `<d>` 台词文本**。
- **10:48:41 / seq4647/4649** 立即对这两条提交 2K 再生成（未审）。
- 用户 **11:02 seq4860**「**啊？谁他妈跟你说参考音频必须是台词音频了？参考是什么意思你不懂吗？真的台词不是靠提示词输入吗？**」；seq4861「不应该是测生成后的音频的 ASR 转录吗」。
- 模型自查 **seq4864**（11:02）：「参考音频不是『台词音频』——reference_audio 是**声线/音色参考**…真正的台词是靠提示词（`<d>[Chinese]台词</d>` 形式）输入的！」并列出正确三步。
- 修正后 **11:02:43 / seq4889**、**11:03:38 / seq4891** 两条都写 `<d>[Chinese]…</d>` + `<Audio 1>` 仅音色 → 768P 均成功（¥1.56 / ¥1.30）。

**根因**：`reference_audio` 的语义（音色 ≠ 台词）没有进入当时的上下文（见 `02_MODEL_PHASES.md` §4：压缩摘要里「音色/台词」出现 0 次）；且旧会话里已验证过的正确写法（9e5b4806 的 `PLAN_v01.json`）没有沉淀到项目规则文件。

**修正**：台词一律写在 `<d>[Chinese]…</d>`；`reference_audio` 只承担音色；生成后用**本地 ASR** 对生成片音轨转录、与批准台词逐字比对（不是拿参考音频去比）。

## F5｜技能文档误导：`minimax-video` skill 没把「2K 直出」与「再生成的源条件」分开（直出限制是真的，源条件那句是错的）

- 产出勘误：`docs/video/H3_LITE_PILOT_20261115/LITE_REGEN_ERRATUM.md`（83 行，未改插件）。
- **该 SKILL 文本至今未改**（`git log -- plugins/dsh-minimax-video/skill/SKILL.md` 只有建仓提交 `9bb14f2` 2026-11-15 17:02:03）。

**分级说明**：
- `:23`「2K only on MiniMax-H3. Highspeed, Lite and Max stop at 768P; 480P exists only on those three.」= **direct generation 的真限制，不算错**；
- `:118`「Source must be a MiniMax-H3 768P output」= **把直出限制外推到再生成源，错**；官方与本地代码只要求物理规格（见上）；
- **已实测**：Lite 768P → 2K 再生成（用户实测 + 项目 task `463851531801158`）；**未实测**：Highspeed/Max 的 768P 源能否再生成（只能按物理 schema 推导，不能称已验证）。

**影响**：主代理据此拒绝用户已实测的路径，等于「文档比实测优先」，浪费一轮并需要开勘误会话。

**修正**：见 `05_PLUGIN_FIXES.md` P2。

- 场景卡：11-13 `8ead16cd`(05:15) → `71b7af9a`(06:05) → `05141dcc`(06:44，用户原话「请你继续会话 session-71b7af9a… 的内容」)→ `3e5104b4`(07:03) → `b57d1453`(07:04，换 Claude 线)。每次都重新读项目、重新解释诉求。
- 片头片尾/海报：`d111fc54`(11-16 00:19) → `213b3228` T1 → `19ae8c03`(10:46) → `830fa7d5`(11:26，用户「session-19ae8c03… 生成个海报咋就那么困难呢？」)。
- 当时的机制限制：DSH 无「续接旧会话」入口，用户只能复制会话 ID 让新会话「接着做」，上下文靠人肉搬运。

**修正**：用 `send_message` 续接已有会话（工具已支持）；确需新会话时，交接文件必须包含 `不变量清单 + 已批准资产索引 + 当前状态 + 禁止事项`，而不是让用户复述。
